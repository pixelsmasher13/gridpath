The real component, not a recording

The engine runs in your browser. Open your own .xlsx in it: nothing is uploaded.

About 1.4 MB the first time, then cached by your browser.

Keep the workbook.

A save patches the original .xlsx: the parts a session changed are rewritten, everything else is copied byte for byte. On a 1.4 MB analyst model, 75 of 76 parts came back identical. The other embeddable spreadsheets we measured dropped custom XML and printer settings, or most of the defined names.

How saving works →

Calculate in the browser.

A Rust engine, a fork of IronCalc, runs in a Web Worker: dynamic arrays, LET and LAMBDA, XLOOKUP, the IFS family. A 55,000-formula model recalculates in 0.8 s; one with 2.3 million cells opens in 4 s. Formulas it can't calculate keep Excel's value, and say so.

What it calculates →

Choose where edits go.

Autosave to the browser, or to your backend with httpStore. The status says which: "Saved to your account". If your backend is down, edits wait in the browser ("Saved in this browser only") and the save retries.

That's a working spreadsheet with a toolbar, autosave and version history. Problems arrive at onError with a code and a hint you can show: an old .xls gets "an old-format .xls workbook", not a blank grid. CSV and other delimited text open as a new workbook.

app/api/agent/route.ts
import Anthropic from "@anthropic-ai/sdk";
import { AGENT_INSTRUCTIONS, agentTools } from "gridpath/agent";

export async function POST(req: Request) {
  const { messages } = await req.json();
  const reply = await new Anthropic().messages.create({
    model: "claude-opus-5-5",
    max_tokens: 16000,
    system: AGENT_INSTRUCTIONS,
    tools: agentTools(),
    messages,
  });
  return Response.json(reply);
}

Confidence before commitment

Test the files your users rely on.

Keeping a file, calculating it and drawing it are different promises. The demo checks each against your own workbook: what it carries, how long it took to calculate, and, after you edit it, which parts a save rewrote.

What does a save keep?

Every part of the file the session didn't touch comes back byte for byte: charts, pivot tables, VBA macros, images, custom XML, defined names, printer settings. The parts with the cells, formats, rows and sheets the session changed are rewritten, and formulas the edits recalculated carry their new results so readers that don't calculate see current numbers.

What isn't supported yet?

Line charts are drawn and update as you edit; other chart types are kept in the file and shown as a placeholder. There are no data-validation dropdowns and no real-time collaboration yet. Not every Excel function is implemented: a formula GridPath can't calculate (an add-in call, an unsupported function, a link to another workbook) keeps the value Excel saved, the toolbar counts them, and getCell says why.

Does the file leave the browser?

Not in the demo: it opens, calculates and saves in your browser and stores your edits there. In your app the file goes where your store sends it, usually your own API; GridPath runs no server for it.

How were the numbers measured?

In Chromium on an M2 Pro, opening each workbook in each component, recalculating, editing one input and saving; fidelity is a part-by-part comparison with the original file and agreement is against Excel's cached results. The harness is in eval/embed-bench; point it at your own files.

Is it open source?

The engine, the in-place saver and the gridpath package (this component and an MCP server for coding agents) are Apache-2.0. GridPath's desktop app, in the same repository, is source-available under FSL-1.1; each release becomes Apache-2.0 two years after it ships.
